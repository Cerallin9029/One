## 持续工作机制

1. 每次执行先检查仓库、未完成 PR、CI 和真实 issue，选择一个可在一次工作中交付的问题。
2. 实现、运行针对性测试、更新必要文档，通过 PR 记录原因和验证。
3. 每周检查上游 Codex 指令行为变化，维护兼容性说明；无变化不制造提交。
4. 发布按实质改进进行，不为填贡献图而发版。
5. 记录每条公开反馈的来源、问题、处理和结果。匿名或私有反馈征得授权后才公开；不计入虚构用户。
6. 申请准备和本地证据记录留在 `docs/`；身份及邮箱等私人表单信息不写入公开材料。

项目构建由助手负责。外部社区介绍、邀请试用、私信和邮件在用户明确授权后再发送。将私有仓库改为公开、配置网络访问以及申请表最终提交如工具需要账号交互，则在具体产物备好后由用户完成该一步。

## 申请准备条件（内部检查，非官方资格）

- 公开仓库包含实际可安装代码、许可、文档和通过的 CI。
- 有真实外部用途或清楚可复现的生态贡献；新项目明确说明新，而不声称广泛采用。
- 维护责任有实际版本、修复、issue 响应和 PR 记录。
- 说明 Codex 如何帮助测试、修复、文档、评审等维护任务；如申请 API credits，列出用途、预算上限和成功指标。
- 官方最新条件和表单已读取；所有陈述与当前事实一致；个人字段由真实账号资料确认。
